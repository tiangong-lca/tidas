TIDAS separates life cycle data semantics, JSON structures, and executable tooling into explicit layers. This overview establishes the object relationships and conformance boundary before linking to individual Schemas.

## LCA object relationships

- A **Process** references **Flows** through exchanges to describe inputs and outputs of a product system.
- A **Flow** uses **Flow Properties** and **Unit Groups** to express comparable quantities.
- **Locations** and taxonomies provide stable classifications for geography, processes, flows, and methods.
- **Contacts** and **Sources** support responsibility, provenance, and traceability; **LCIA Methods** and **Life Cycle Models** carry impact-assessment and system-model references.

## Conformance ladder

1. Parseable JSON: the document syntax is valid.
2. Schema conformance: fields, types, and local constraints pass JSON Schema validation.
3. Package and reference integrity: directories, IDs, versions, and cross-document references agree.
4. Conversion profile: the package is checked against the declared versions of the Schema, XSD, XSLT, and rules assets.
5. LCA fitness: system boundaries, representativeness, allocation, and review still require methodological judgement.

> **Normative boundary:** the machine-executable boundary consists of Schemas marked normative by the inventory plus the locked assets and rules actually applied by the selected validation profile. “Normative” is a role declared by that versioned inventory; navigation, diagrams, examples, and integration patterns on this site are informative and add no constraints.

## Minimum-package path

1. Start with a [Process](/en/docs/core-modules/schema/schema-content/json-schema-processes/) dataset.
2. Add every referenced Flow, Flow Property, Unit Group, Contact, and Source.
3. Use `tidas validate --schema-only` for structural diagnosis, then run full `tidas validate` for package and reference checks.
4. Record the effective contract, assets, and runtime fingerprints with `tidas version --format json`.
